**Metric definitions to put into the specification**

- Effort variance (hours) = actual hours − baseline estimated hours.
- Budget consumption (%) = actual hours / budgeted hours × 100. Apply 90%/100% thresholds to this measure, with configurable thresholds.
- Estimate at completion (hours) = actual hours + separately maintained remaining estimate. Remaining effort must not simply become zero when the original estimate is exhausted.
- Direct delivery contribution = revenue on an explicitly chosen basis − direct delivery costs. This is a currency amount; it is not a complete accounting profit measure.
- Contribution margin (%) = direct delivery contribution / revenue × 100. Show N/A when revenue is zero; distinguish forecast, approved billable amount, invoiced amount and received payment. Keep invoice/accounting automation outside the initial PMT scope.
- Estimation bias (%) = (actual − baseline estimate) / baseline estimate × 100, for completed, estimated work. Positive means actual exceeded estimate.
- Available delivery capacity = scheduled working hours − holidays/leave − reserved non-project time. Define each deduction once to avoid double subtraction.
- Defect leakage (%) = externally discovered defects / (internally + externally discovered defects) × 100, for the same release and defined observation window. Zero total defects means N/A, not proof of perfect quality. This is a proposed definition to standardize across KS-PMT.

The increments define dependency order, not duration estimates. Client delivery should precede advanced analytics and employee scoring. Existing core acceptance work should be completed within each relevant release. Native field features, geofencing, broad CRM/HR expansion, employee leaderboards and a universal automation designer have lower priority for the stated focus.

**Example acceptance criteria for the next specification revision**

- Two licensed clients can vote on the same published idea, but neither can read the other's originating private ticket, attachments, contact details or business-impact statement.
- A client approves change request revision 3. Editing cost or scope creates revision 4 requiring new approval; revision 3 remains readable in history.
- A developer with a four-day, 32-hour schedule and one eight-hour approved absence has 24 expected loggable hours for that week; browser focus changes do not stop their work session.
- The same delivery defect can resolve several client requests, while each client retains its own communication and acceptance history.
- A released product version does not automatically mean an on-premise client's installed version has changed. Track the client's accepted/current version manually where relevant; no deployment integration is required.

My first five feature priorities are requirements/acceptance traceability, change-request approval, client UAT/sign-off, client progress updates, and backlog/sprint planning with basic blockers. Saved views are an accompanying daily-productivity priority already proposed in earlier documentation. The portal and voting engine should remain on the roadmap, with the boundaries above defined before implementation.
